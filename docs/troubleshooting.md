# Troubleshooting

Find the symptom, check the cause, apply the fix. Commands assume the defaults (RESP on 6379, admin on 9379). In Kubernetes, prefix with `kubectl -n goredis` and use `kubectl logs`/`describe` instead of `docker logs`/`inspect`. For alert-driven incidents see [incidents.md](incidents.md).

| Symptom | Likely cause | Fix |
|---------|--------------|-----|
| `Connection refused` on 6379 | The server is not running, is still replaying the AOF, or listens on another address. In Docker: the port is not published, or published on a different host interface. | Check the process: `docker ps -a`, `docker logs goredis` (or `kubectl get pod`, `kubectl logs`). Check `/readyz` returns 200. Check the effective `GOREDIS_ADDR`: inside a container it must be `0.0.0.0:6379` (the image default), not `127.0.0.1`. Check the port mapping with `docker port goredis`. In Kubernetes, also check the NetworkPolicy (a blocked connection usually times out rather than being refused). |
| Server exits at startup: protected mode refuses to start | `GOREDIS_ADDR` is not a loopback address (for example `0.0.0.0` in the container) and no password is configured. | Set a password: `GOREDIS_REQUIREPASS` or `GOREDIS_REQUIREPASS_FILE` (Kubernetes uses the `goredis-auth` Secret). For local development only, with host ports bound to 127.0.0.1, set `GOREDIS_PROTECTED_MODE=false`. |
| `-NOAUTH Authentication required.` | A password is configured and the client did not send `AUTH`. | Send `AUTH <password>` or `AUTH default <password>` first (`redis-cli -a ...`, or the password option of your client library). If a password was just added or rotated, update every client. |
| `-MISCONF Errors writing to the AOF file: ...` on writes | The AOF cannot be written or fsynced: disk full, read-only volume, I/O error. Reads still work. | Check free space on `/data` and the server logs. Free or expand the disk; writes resume automatically after the next successful retry (every second). Then run `BGREWRITEAOF`. After an fsync error the AOF stays unhealthy until a successful `BGREWRITEAOF` or a restart. Full procedure: [incidents.md, Incident 2](incidents.md#incident-2-aof-disk-full-and-persistence-write-failures). Do not restart first: buffered writes would be lost. |
| `-OOM command not allowed when used memory > 'maxmemory'.` | The estimated dataset exceeds `GOREDIS_MAXMEMORY`. goredis does not evict keys. | Delete keys or set TTLs on the client side, or raise `GOREDIS_MAXMEMORY` together with the container memory limit and `GOMEMLIMIT` ([kubernetes.md](kubernetes.md#memory-limits-gomemlimit-and-goredis_maxmemory)). Check `goredis_dataset_bytes` against `goredis_maxmemory_bytes`. |
| Container restarts with exit code 137 / `OOMKilled` | The process used more memory than the container limit (often `GOREDIS_MAXMEMORY=0` and no `GOMEMLIMIT`). | Set `GOREDIS_MAXMEMORY` well below the limit and `GOMEMLIMIT` to about 90% of it. See [incidents.md, Incident 1](incidents.md#incident-1-container-oomkilled). |
| `-ERR max number of clients reached` | `GOREDIS_MAX_CLIENTS` (default 1000) connections are open. Often a client that leaks connections. | Check `goredis_connected_clients` and `goredis_rejected_connections_total`. Fix the leaking client or size its pool. Idle connections close after `GOREDIS_IDLE_TIMEOUT` (5m). Raise `GOREDIS_MAX_CLIENTS` only for legitimate load. |
| `-ERR command 'X' is disabled by server configuration` | The command is listed in `GOREDIS_DISABLED_COMMANDS` (Kubernetes disables `FLUSHDB`). | Intended for dangerous commands. If a client needs the command, remove it from the list and restart. If this appeared right after a deploy, see [incidents.md, Incident 3](incidents.md#incident-3-a-bad-release-raises-latency-or-errors). |
| Startup fails: the AOF lock is held by another process | Another goredis process (or container/pod) uses the same data directory and holds `<aof>.lock` (`/data/appendonly.aof.lock`). | Find and stop the other instance: `docker ps` for containers sharing the volume; in Kubernetes, an old pod still terminating (`kubectl get pods`; the Deployment uses `Recreate` to prevent this). Do not delete the lock file to "fix" it: the lock is held by the running process, and two writers would corrupt the AOF. A stale lock file left by a crashed process is not a problem, because the OS releases the lock when the process exits. |
| Startup refused: corrupt AOF | A record in the middle of the AOF is invalid (disk error, manual edit, a copy of a file being written). An incomplete record at the very end is truncated automatically when `GOREDIS_AOF_LOAD_TRUNCATED=true`; corruption mid-file always stops startup. | With the server stopped, inspect: `goredis-check-aof /data/appendonly.aof`. Repair: `goredis-check-aof -fix /data/appendonly.aof`, which writes a backup of the original first and then repairs the file. Records after the corruption point can be lost, so keep the backup until you have checked the result with another `goredis-check-aof` run. In Docker: `docker run --rm -v goredis-data:/data --entrypoint goredis-check-aof goredis:dev -fix /data/appendonly.aof`. In Kubernetes: scale to 0, run a Job with the same image and the PVC mounted, then scale back to 1. |
| `/readyz` returns 503 for a long time after start (pod not Ready) | The server is replaying a large AOF. Readiness turns 200 only after the AOF is loaded and the listener accepts. | Wait, and check the logs for replay progress. `goredis_aof_recovered_commands` shows the replayed count once loaded. If the startup probe kills the container before replay ends (restarts with `Startup probe failed`), raise `startupProbe.failureThreshold`. Run `BGREWRITEAOF` regularly so replays stay short. A 503 that appears on a running server means it is shutting down. |
| `permission denied` on `/data` at startup | The volume is not writable by uid 65532. Common with bind mounts and with Kubernetes volumes when `fsGroup` is missing. | Docker bind mount: `sudo chown 65532:65532 /path/on/host`. A named volume gets the right owner automatically. Kubernetes: keep `securityContext.fsGroup: 65532` (in `deployment.yaml`); some volume types (hostPath, some NFS) ignore `fsGroup`, so fix ownership on the storage side. |
| Docker health status stays `starting` or becomes `unhealthy` | `/readyz` is not 200 (still loading, or shutting down), or the admin server is disabled (`GOREDIS_ADMIN_ADDR` empty). | `docker inspect --format '{{json .State.Health}}' goredis` shows the probe output. If you disable the admin server on purpose, run with `--no-healthcheck`. |
| Pod `Pending` or stuck in `ContainerCreating` with `Multi-Attach error` | The PVC is not bound (no default StorageClass), or the ReadWriteOnce volume is still attached to a node from an old pod. | `kubectl describe pvc goredis-data` and `kubectl describe pod`. Set `storageClassName` if there is no default class. For multi-attach, wait for the old pod to terminate; this is why the Deployment uses `strategy: Recreate`. |
| Prometheus target down but the server works | NetworkPolicy blocks 9379 from the Prometheus namespace, or the admin server listens on loopback only. | The policy allows the namespace named `monitoring`; change it if Prometheus runs elsewhere. `GOREDIS_ADMIN_ADDR` must be `0.0.0.0:9379` in a container. |
